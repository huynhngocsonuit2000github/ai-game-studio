# Studio V5.2 context and evidence

## Work read protocol

1. Resolve the approved target and fetch GitHub main. Record its full SHA and the approved requirement IDs and paths.
2. Read the root contract, applicable Studio rules, canonical registry entry, game instructions, state, checkpoint, decisions and QA. Read only the code, stages, assets metadata and build flags needed to check that scope. Treat published URLs, rights and scope as evidence-backed observations. Use chat to recover Producer intent and corroborate it against recorded decisions.
3. Check the deployment workflow and live build marker. Compare the observed SHA with current main. Verify the public entry and affected behavior when accessible, then record the delta between merged source, the actual assembled artifact and the observed deployment.
4. If Work lacks GitHub access, Codex can supply the same compact snapshot from its authorized checkout. Include the SHA, scoped paths, approvals, evidence links, unknowns and changes since the prior checkpoint. Verify ZIP attachment readability independently by reading the actual bytes.

## Codex write and resume protocol

Fetch main before every existing-game feature, import, resume or review. Compare the recorded or supplied baseline with current main, preserve local edits and identify changes affecting the approved behavior. Record the inspected SHA, scope, deviations and evidence. Implement and test the authorized delta, update state and QA, and publish one PR for the coherent batch. Use PR head and CI tested revision metadata for candidate identity. Use GitHub main for merged identity and the live marker plus observed checks for deployed identity. Keep merge manual.

For packs, retain the [V5.1 manifest and independent approval](WORKFLOW_V5_1.md) and use one ZIP with one external master prompt. Record the baseline and the expected behavior in the feature brief. If the pack is stale, compare its pinned base with current main, including exact destinations, dependencies, save contract and approval/rights records. Compare with the isolated before/after review at the pinned revision only when that revision is a trusted ancestor. Reject divergent/unverifiable bases, changed replacement targets, destination collisions, incompatible behavior or conflicting scope. Obtain a revised pack and independent approval for changed bytes, replacements or scope. A stale pinned pack still fails validation against current HEAD. A compatible reviewed delta may be reissued against current main under the existing contract. Never rewrite a digest or baseline in place to pass validation. Additive packs with a null base still require current context sync, destination collision checks and existing independent approval.

On resume, recover the existing branch, PR, last verified SHA, approved scope, pack digest, gates and outstanding checks. Reconcile changes since that checkpoint before using prior results. Keep earlier evidence tied to its tested revision. Record what needs rerunning and why. Read-only review follows the same context sync. If trusted scope or another gate blocks delivery, leave a draft PR and a checkpoint with the exact blocker.

## Game state version 1

Adopt `games/<id>/production/GAME_STATE.json` when a game next needs state tracking. Use the [template](../templates/game/production/GAME_STATE.example.json) and run `node scripts/game-state.mjs` after normal Pages assembly. Registry is authoritative for catalog fields. State links decisions, source, checkpoints and QA instead of repeating catalog metadata. Use local game-relative references or HTTPS links. A reference identifies evidence to inspect. The validator checks local file presence and URL form.

- `baselineCommit` is a full SHA for the inspected strict ancestor of the state-bearing revision. Refresh the assessed baseline when behavior, flags or scope changes. The state file carries no candidate or merged self-SHA.
- `records` uses unique stable lowercase IDs and kinds `feature` or `level`. Implementation is `planned` or `implemented`. Public availability is `unknown`, `private` or `public` and describes packaging under the canonical production registry. A public record requires implementation, approved preview or release evidence, cleared rights, a manifest entry and PASS evidence for that record on the normal assembled Pages artifact. Derive authored level count from level records and public level count from public level records. Include planned authored levels as records. Artifact checks use target `assembled-pages`, `private-fixture`, or null when unchecked.
- Acceptance is `unknown`, `pending` or `accepted`. Cite an explicit Producer decision for acceptance, including its scope and any limitations on build identity. CI records technical results.
- `save` is null when unknown or inapplicable (explain in known gaps), or records schema ID, positive version and evidence. `publication` records rights (`unknown`, `pending`, `cleared`), preview (`unknown`, `pending`, `approved`), release (`unknown`, `blocked`, `approved`) and evidence for the specified scope. Existing rights and release gates still apply.
- `deployment` records `deployedCommit`, URL, UTC observation time and separate `revision`, `http` and `gameplay` checks. Null means unknown or unobserved. Compare the deployed SHA with current main before using results as current. An older successful deployment remains historical evidence. A current HTTP/revision pass says only that the routes and build marker responded.
- A check records `PASS`, `FAIL`, `NOT_RUN` or `BLOCKED` and evidence. `NOT_RUN` means the check was unattempted or intentionally deferred. `BLOCKED` identifies a prerequisite or access issue. A failed proxy request does not establish the site's status. State why any check was skipped or blocked.

## Requirement evidence

Use one row per approved requirement in the [feature brief](../templates/FEATURE.md). Write the expected player behavior and actual implementation, evidence tied to the tested SHA and artifact, result and deviations. Build and serve the normal assembled Pages output with the canonical registry and production flags. A private fixture can verify candidate behavior only. For level expansions, progress normally from a fresh start through every level, inspect the next-level controls, reload an earned save and exercise previous saves or migration, reach final victory, and check runtime asset requests. Check direct entry, catalog launch and return. Associate each claimed public level with evidence from that run.

Use the existing Pages workflow summary for deployed SHA and HTTP evidence. Live gameplay requires a browser route with game-specific expectations. When unavailable, record NOT_RUN and use the manual checklist in the [Pages runbook](../../deployment/README.md) during the next authorized verification. A passing local artifact remains candidate evidence until a live observation exists.
