# Production contract — V5.1
## Repository and runtime
Use strict TypeScript, reproducible lockfile, pinned toolchain, explicit scripts, independent game entry points and game-specific builds. Registry IDs are lowercase kebab-case and immutable; routes are derived from IDs, not arbitrary URLs. The portal and every 2D and 3D game must support GitHub Pages project-subpath hosting. Each game ships an independent static HTML entry point and loads only on navigation. Use relative URLs for scripts, styles, images, audio, models, textures, workers, WASM and decoder files. Provide a relative link back to the portal. Avoid server rewrites, backend dependencies and required custom response headers. Namespace localStorage by game ID and save schema. No backend or accounts unless approved. Shared packages are optional, versioned and tested. Do not commit node_modules, dist, caches, secrets or unlicensed assets. Large source assets need an approved storage strategy; do not assume unlimited GitHub storage or Pages capacity.

## Stage contract
Every game includes design/GDD.md, ART_DIRECTION.md, TECH_DESIGN.md, AUDIO_PLAN.md; production/PROGRESS.md, DECISIONS.md, ASSET_MANIFEST.csv; stages/<stage>/STAGE.md; reports/; assets/concept, assets/source, assets/runtime. Stage document must specify dependency, task IDs, player outcome, scope exclusions, asset IDs, implementation contracts, test scenarios, measurable acceptance, preview and stop conditions. Use ready/in_progress/blocked/candidate_ready/accepted; acceptance requires evidence and approval where specified. No task is complete merely because a file exists.

Execute an authorized batch through one scoped PR. Named stage batches can defer expressly identified intermediate Producer reviews and must validate every included stage in order. G0 design and G4 release require actual Producer decisions. G2 review can be deferred only when explicitly authorized for the named batch. Keep technical evidence, Producer playtest acceptance, and publication decisions distinct in the checkpoint.

## Handoff and feature lifecycle

Scope prompt-only and ZIP tasks to the exact game ID. Follow the [V5.1 handoff](WORKFLOW_V5_1.md) for pack validation, provenance and rights. Use the [feature brief](../templates/FEATURE.md) to capture ID, baseline, version, save compatibility, regression, rollback and acceptance for features and expansions. Extend the existing checkpoint while preserving its previously accepted stage and release evidence.

## Asset pipeline
Manifest fields: id,type,description,stage,source,license,source_path,runtime_path,format,budget,animation_clips,status,validation. Status planned/generated/imported/verified/missing. Track actual source and rights; concepts are not runtime assets. For 2D check transparency, atlas frames, alignment, pixel density, readable silhouettes. For 3D check GLB import, transforms, bounds, material, rig, clips, triangles and preview renders. Audio checks include loop, clipping, mute and user-gesture unlock. Local Blender CLI and image/audio tools optional; record versions and command outputs. Verify generator availability in cloud; blocked assets must remain explicitly missing. Never silently substitute final placeholders.

## Testing and budgets
Per-game target device, browser, initial transfer, total runtime bytes, FPS/frame time, memory and loading targets must be specified in tech design. Default planning targets: desktop 60 FPS, 2D initial transfer <= 10 MB and total <= 50 MB, 3D initial <= 25 MB and total <= 100 MB; revise with Producer approval. These are targets, not measured results. Automated gameplay tests cover boot, inputs, full core loop, failure/restart, pause/resume, resize, save where applicable, asset/audio loads and console errors. Capture actual screenshots and performance environment. Label PASS/FAIL/NOT_RUN/BLOCKED. Require Producer approval for player-visible stages under the stage contract. No P0/P1 defects at G3/G4.

## Preview and deployment
GitHub Pages is the primary host. GitHub Actions runs frozen installs, lint, type checks, unit tests, project-subpath browser smoke tests and artifact checks on PRs and main. Only a verified push or manual run from current `main` can deploy. Configure Pages to use GitHub Actions and restrict the `github-pages` environment to main. Keep deployment credentials in the deploy job. Record the published URL and commit after the workflow verifies the revision.

Each Pages release contains the complete static site. Rebuild public releases and explicitly approved public development previews from versioned sources or artifacts with verified provenance. Retain previously released entry paths, including during rollback. A public development preview can be withdrawn. Each game package builds to an independent static `dist/`. Public visibility requires explicit approval and asset clearance. The portal labels public development builds as In Development. Development fixtures stay out of the release artifact.

For pre-merge checks, serve the built candidate locally under a project subpath and retain browser evidence. PR artifacts are downloadable evidence. Docker is optional. Use an explicitly configured preview host when a shareable preview is required. Roll back through an authorized revert PR on main and verify the replacement deployment and commit. A verification failure before deployment leaves the existing site online.

## Pages acceptance criteria for games
For every 2D or 3D game, build from a clean install and load both the portal and the game under the Pages project subpath. Open the game via the catalog and its direct URL, run representative gameplay, check runtime asset and worker requests for missing files or incorrect paths, and follow the return link to the portal. Test a production build and record the tested commit, evidence, and limitations. Check that the release artifact excludes development-only and unpublished content before deployment.

## Evidence and feedback
Progress: target, milestone, task IDs, base/candidate commit, scope, commands/exit codes, evidence paths, known issues, blockers, approval status, next ready task. Feedback: game ID, version, URL, steps, expected/actual, screenshot, severity, regression test. Producer approves gameplay, not code; agent owns tests and technical review. No automatic approval or fabricated logs. Do not alter unrelated games to fix a target. Keep task context bounded.
