# Production contract
## Repository and runtime
Use strict TypeScript, reproducible lockfile, pinned toolchain, explicit scripts, independent game entry points and game-specific builds. Registry IDs are lowercase kebab-case and immutable; routes are derived from IDs, not arbitrary URLs. Portal must support subpath hosting and relative asset URLs. Prefer independent static game pages loaded on navigation (no eager download of every game). Provide a way back to the portal. Namespace localStorage by game ID and save schema. No backend or accounts unless approved. Shared packages are optional, versioned and tested. Do not commit node_modules, dist, caches, secrets or unlicensed assets. Large source assets need an approved storage strategy; do not assume unlimited GitHub storage or Pages capacity.

## Stage contract
Every game includes design/GDD.md, ART_DIRECTION.md, TECH_DESIGN.md, AUDIO_PLAN.md; production/PROGRESS.md, DECISIONS.md, ASSET_MANIFEST.csv; stages/<stage>/STAGE.md; reports/; assets/concept, assets/source, assets/runtime. Stage document must specify dependency, task IDs, player outcome, scope exclusions, asset IDs, implementation contracts, test scenarios, measurable acceptance, preview and stop conditions. Use ready/in_progress/blocked/candidate_ready/accepted; acceptance requires evidence and approval where specified. No task is complete merely because a file exists.

## Asset pipeline
Manifest fields: id,type,description,stage,source,license,source_path,runtime_path,format,budget,animation_clips,status,validation. Status planned/generated/imported/verified/missing. Track actual source and rights; concepts are not runtime assets. For 2D check transparency, atlas frames, alignment, pixel density, readable silhouettes. For 3D check GLB import, transforms, bounds, material, rig, clips, triangles and preview renders. Audio checks include loop, clipping, mute and user-gesture unlock. Local Blender CLI and image/audio tools optional; record versions and command outputs. Verify generator availability in cloud; blocked assets must remain explicitly missing. Never silently substitute final placeholders.

## Testing and budgets
Per-game target device, browser, initial transfer, total runtime bytes, FPS/frame time, memory and loading targets must be specified in tech design. Default planning targets: desktop 60 FPS, 2D initial transfer <= 10 MB and total <= 50 MB, 3D initial <= 25 MB and total <= 100 MB; revise with Producer approval. These are targets, not measured results. Automated gameplay tests cover boot, inputs, full core loop, failure/restart, pause/resume, resize, save where applicable, asset/audio loads and console errors. Capture actual screenshots and performance environment. Label PASS/FAIL/NOT_RUN/BLOCKED. Human approval is required at G0, G2 and G4; also require Producer approval for each player-visible stage unless explicitly waived. No P0/P1 defects at G3/G4.

## Preview and deployment
Local: Docker Compose serves static builds at localhost:8080 (configurable), health check and previous known-good image rollback. Build before switching; failure must preserve last working build. Local runner executes Docker; Codex Cloud must not claim access to the Producer's localhost. Cloud: GitHub Actions validates changes, uploads PR build/test artifacts, deploys verified main to Pages after authorized merge. Default portal links to approved stable builds; development builds clearly labeled. Pages is one static deployment: preserve every previously published game when rebuilding; never deploy only the changed game's dist over the entire site. Use cached unchanged builds only with verified provenance, otherwise rebuild. PR artifacts are not public preview URLs. For pre-merge playtest, use local Docker from candidate branch or an explicitly configured preview host; if unavailable mark preview blocked. Do not silently merge to get a preview. Record SHA, build ID, URL, actual smoke results and rollback steps. Release game visibility requires explicit approval; a static dashboard is not an access-control boundary.

## Evidence and feedback
Progress: target, milestone, task IDs, base/candidate commit, scope, commands/exit codes, evidence paths, known issues, blockers, approval status, next ready task. Feedback: game ID, version, URL, steps, expected/actual, screenshot, severity, regression test. Producer approves gameplay, not code; agent owns tests and technical review. No automatic approval or fabricated logs. Do not alter unrelated games to fix a target. Keep task context bounded.
